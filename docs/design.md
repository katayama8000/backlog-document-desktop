# backlog-document-desktop 設計書

- 作成日: 2026-11-07
- 状態: フェーズ1（読み取り専用の試作）

## 1. 概要

Backlog のドキュメントを、デスクトップアプリで閲覧・編集するためのクライアント。

- 本文は TipTap による見たまま編集（WYSIWYG）。
- Backlog の公開 API を使って同期する。
- 他のユーザーの編集と衝突した場合も、変更を失わない。

### 技術の構成

- Tauri 2
- フロントエンド：React 19 + TypeScript 7 + Vite（画面のみを担当）
- Rust：API 呼び出し、認証、同期、3者マージ、ローカル保存を担当

ロジックは Rust に寄せる。フロントエンドは表示と入力に専念する。

| 項目 | 決定 |
| --- | --- |

| 衝突時の扱い | 衝突コピーを保存（③a）→ 3者マージ（③b）→ 衝突画面（③c） |
| エディタ | TipTap |
| UI ライブラリ | 使わない（素の CSS） |

## 3. 前提となる API 仕様と制約

### 3.1 使用する API

| 用途 | API | 備考 |
| --- | --- | --- |
| ツリー取得 | `GET /api/v2/documents/tree?projectIdOrKey=` | |
| 一覧取得 | `GET /api/v2/documents` | `sort=updated` で変更を検知する |
| 本文取得 | `GET /api/v2/documents/:id` | `plain` は Pandoc Markdown（正規形） |
| 新規作成 | `POST /api/v2/documents` | `content` は Markdown として解釈される |
| 本文更新 | `PATCH /api/v2/documents/:id/content` | `content` に本文全体の Markdown。レスポンスに本文は含まれないので取得し直す。`markdownIsFallback` が真なら保存はされたが Markdown を再生成できていない（③a ではそのドキュメントを読み取り専用にする） |
| タイトル更新 | `PATCH /api/v2/documents/:id` | タイトルと絵文字のみ。③では未使用 |


### 3.2 同期設計に効く制約

1. **バージョン情報がない**
   - 変更の目印は `updated`（秒単位）だけ。
   - そのため本文のハッシュも併用する。
2. **更新 API はまだ公開されていない**
   - ③の細部（送信後のレスポンスの扱い、エラー時の再試行など）は、公開された仕様に合わせて決める。
   - ここでは、更新 API が「本文の Markdown を丸ごと受け取り、サーバー側で現在の本文に反映する」形だと仮定して設計する。
   - この形だと、**取得後に他の人が加えた変更は、送った本文に含まれていなければ消える**。そのため、送信前に最新を取り込む処理（§6）はクライアントの責任になる。
3. **本文は正規化される**
   - 取得できる `plain` は、サーバーが正規化した Markdown。送った文字列がそのまま保存されるとは限らない。
   - 送信が成功したら、取得し直した `plain` を新しいベースにする。

- `doc-sync-engine` は通信も DB も触らない。「ベース・ローカル・リモートを受け取り、次に何をすべきかを返す」だけにして、単体テストで網羅する。
- I/O の組み立て（取得 → 判定 → 送信 → 保存）は `app` クレートが担当する。

## 6. 同期の設計

### 6.1 ドキュメントごとに保持する状態

| 項目 | 内容 |
| --- | --- |
| `base_plain` | 最後にサーバーと一致していた本文（サーバーが正規化したもの） |
| `base_updated` | そのときの `updated` |
| `base_hash` | `base_plain` のハッシュ（SHA-256） |
| `local_plain` | ローカルで編集中の本文。未編集なら `NULL` |
| `read_only` | 編集禁止か（本文を Markdown として安全に扱えない場合など） |

### 6.2 状態遷移

```
            取得
 (未取得) ───────▶ Synced ◀───────────────────┐
                    │ 編集                      │ 送信成功           
                    ▼                          │
               LocalModified ── 送信クリック ──▶ Pushing
                    ▲                          │ リモートが変わっていた
                    │ 衝突を解決                 ▼
                    └──────────────────── Conflicted

 どの状態からでも: 本文を安全に扱えないと判定 → ReadOnly（編集禁止）
```

- リモートだけが変わった場合（ローカルは未編集）：取得し直して、そのまま Synced にする。

### 6.3 送信の手順（「Backlog へ反映」をクリックしたとき）

1. `GET /documents/:id` でリモートの最新を取得する。
2. `doc-sync-engine::plan_push(base, local, remote)` で次の行動を決める。
   - **リモートが未変更**（`updated` もハッシュも `base` と一致）→ `local` を送る。
   - **リモートが変更済み**
     - ③a：`Conflict` を返す。
     - ③b 以降：3者マージを試す。
       - 自動でマージできた → マージ結果を送る。
       - 同じ箇所を両方が編集していた → `Conflict` を返す。
3. 更新 API で送る。
   - **成功**：最新の `plain` を `base` にして、`local` を `NULL` にする。エディタの内容も、この `plain` で置き換える。
   - **送信中に他の編集と衝突したことを示すエラー**：手順1からやり直す（最大3回）。超えたらエラー表示。
   - 具体的なレスポンスやエラーの扱いは、更新 API の公開仕様に合わせる。
4. `Conflict` になった場合
   - ③a：`local` を衝突コピー（`conflict_copies` テーブル）に保存する。
   - エディタはリモートの最新を `base` にした状態に戻し、「衝突コピーがあります」と表示する。
   - ユーザーは衝突コピーを見ながら、手で反映し直す。

### 6.4 残るリスク

- 手順1の取得から手順3の送信までの間（数百ミリ秒）に他の人が編集すると、その変更は消える（§3.2 の2）。
- API に条件付き更新（元にした版を指定し、違えば失敗させる仕組み）がない限り防げないため、このリスクは受け入れる。
- クライアント側では、隙をできるだけ短くする。
  - 手順1〜3の間にユーザー操作や重い処理を挟まない。
  - 3者マージは手順1の取得直後に行い、すぐに送信する。
  - 衝突画面で解決した場合は、解決後に手順1からやり直す。ユーザーが考えている間の変更を取りこぼさないため。

### 6.5 リモートの変更の検知

- ドキュメントを開いたときに取得する。
- 開いている間は一定間隔でポーリングする。間隔は API のレート制限を調べて決める（§10）。
- ローカルが未編集なら、表示を自動で更新する。
- ローカルが編集中なら、「リモートが更新されています」と表示するだけにする（取り込みは送信時に行う）。

### 6.6 3者マージ（③b）

- `diffy::merge(base, local, remote)` を使い、行単位でマージする。
- 比較する3つの本文は、どれも「サーバーが正規化した Markdown」か、「同じ TipTap のシリアライザで出力した Markdown」に揃える。揃っていないと、誰も編集していない箇所まで差分になる（§10 の調査1）。

## 7. ローカル保存（SQLite）

```sql
CREATE TABLE documents (
  id              TEXT PRIMARY KEY,
  project_id      INTEGER NOT NULL,
  parent_id       TEXT,
  title           TEXT NOT NULL,
  base_plain      TEXT,
  base_updated    TEXT,       -- ISO 8601
  base_hash       TEXT,
  local_plain     TEXT,       -- 未編集なら NULL
  read_only       INTEGER NOT NULL DEFAULT 0,  -- 編集禁止
  fetched_at      TEXT NOT NULL
);

CREATE TABLE conflict_copies (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  document_id     TEXT NOT NULL REFERENCES documents(id),
  local_plain     TEXT NOT NULL,
  remote_plain    TEXT NOT NULL,
  remote_updated  TEXT NOT NULL,
  created_at      TEXT NOT NULL,
  resolved_at     TEXT
);

-- API レスポンスを JSON のまま保持する（プロジェクト一覧、ドキュメントツリー）。オフライン閲覧用
CREATE TABLE cache (
  key        TEXT PRIMARY KEY,   -- 'projects' / 'tree:{projectKey}'
  json       TEXT NOT NULL,
  fetched_at TEXT NOT NULL
);

-- Backlog に保存されたファイル（添付画像、共有ファイルの画像）。オフライン閲覧用
CREATE TABLE assets (
  key          TEXT PRIMARY KEY,   -- 'attachment/{documentId}/{attachmentId}' / 'shared-file/{projectKey}/{fileId}'
  content_type TEXT NOT NULL,
  bytes        BLOB NOT NULL,
  fetched_at   TEXT NOT NULL
);

CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL          -- スペースの URL、対象プロジェクトなど。秘密情報は入れない
);
```

- DB は Tauri の app data ディレクトリに置く。
- API キーとトークンは DB に入れず、キーチェーンに保存する。

## 8. 認証

| 段階 | 方式 | 保存先 |
| --- | --- | --- |
| ①〜③ | API キー（クエリパラメータ `apiKey`。公開ドキュメントで保証されている方式） | macOS キーチェーン（`keyring`） |
| ④ | OAuth 2.0 認可コード方式 | 同上（アクセストークン・リフレッシュトークン） |

### 8.1 接続設定（①〜③）

ユーザーが入力するもの：

| 項目 | 例 | 保存先 |
| --- | --- | --- |
| スペースの URL | `https://example.backlog.jp` | SQLite `settings`（`space_url`） |
| API キー | Backlog の個人設定で発行したもの | キーチェーン（サービス名 `backlog-document-desktop`、アカウント名はスペースの URL） |
| 対象プロジェクト | `PROJECT_KEY` | SQLite `settings`（`project_key`）。最後に選んだものを保持する |

流れ：

1. 起動時に `space_url` とキーチェーンの API キーがそろっていなければ、設定画面を出す。
2. 「接続」を押したら、`GET /api/v2/users/myself` を呼んで接続できるか確認する。
   - 成功したら保存し、プロジェクト選択に進む。
   - 失敗したら保存せず、エラーを表示する（URL の誤り、キーの誤り、ネットワークエラーを区別する）。
3. 2回目以降は、保存済みの情報で自動的に接続する。
   - オフラインの場合は、確認をせずにキャッシュの閲覧に入る。
4. 設定画面からいつでも変更できる。スペースを変えた場合は、キャッシュ（`documents` と `conflict_copies`）を消す。

スペースの URL は、末尾の `/` やパスを取り除き、`https://{space}.backlog.jp`（`.com` / `.backlogtool.com`）の形に正規化して保存する。

### 8.2 OAuth（④）

- 設定画面の「Sign in with Backlog」で、ブラウザに認可画面（`/OAuth2AccessRequest.action`）を開く。`state` と PKCE（S256）を付ける。
- アプリはリダイレクト URI（既定 `http://127.0.0.1:53682/callback`）で待ち受け、`state` が一致したリクエストからコードを受け取る。別のパスや `state` のリクエストには 404 を返して待ち続ける。5 分で打ち切り、画面から中止もできる。
- コードを `POST /api/v2/oauth2/token` でトークンに換え、`GET /users/myself` で確認してから保存する。
- アクセストークンは期限の 60 秒前に、リフレッシュトークンで更新する。`401` が返ったときも 1 回だけ更新して送り直す。更新したトークンはキーチェーンに保存する。
- キーチェーンの項目はスペースごとに 1 つで、API キーかトークン（JSON）のどちらかを入れる。起動時の読み取りが 1 回で済み、片方でサインインするともう片方は消える。
- `client_id` / `client_secret` / リダイレクト URI はビルド時に埋め込む（`BACKLOG_OAUTH_*`、`src-tauri/build.rs`）。リポジトリは公開なので、値はコミットしない。埋め込んだ `client_secret` はバイナリから取り出せる。
- 埋め込みのないビルドは API キーだけを使う。API キーは、開発用の `.env` と、OAuth を使えないときの代わりとして残す。
- 未確認（§10）：リダイレクト URI に `http://127.0.0.1` を登録できるか。PKCE のパラメーターを Backlog が使うか（使わなくても無視されるだけで、`state` で CSRF は防げる）。

「標準や Tauri で足りるものは足さない」を原則とする。

### 10.1 調査結果（2026-11-07）

**調査1・2（暫定）**：Pandoc 特有の要素を含むサンプル（約40行）を作り、TipTap 3.33（StarterKit + TableKit + @tiptap/markdown）で Markdown → TipTap → Markdown を往復させた。

| 要素 | 結果 |
| --- | --- |
| 見出しの ID `## 見出し {#abc}` | **保持される**。ただし属性として解釈されず、見出しの文字列の一部として残る（画面に `{#abc}` が表示される） |
| コードブロックの属性 ` ```{#def} ` / ` ```typescript {#ghi} ` | 保持される（言語名の文字列として残る） |
| 行末スペース2つの改行、引用、太字、インラインコード、リスト、水平線 | 一致 |
| 表 | **差分が出る**。セル幅に合わせた空白の詰め物が入り、表の前後に空行が1行ずつ増える。内容自体は保持される |

対応方針：

- 表の差分は空白だけなので、③で比較・マージする前に、表の行の空白と連続する空行を正規化してから比較する。送信内容はサーバーが正規化し直すので、問題にならない見込み。
- 見出し ID が画面に見えるのは見た目の問題。③までに、`{#...}` を非表示にするか、属性として保持するカスタム拡張を検討する。
- サンプルでの確認なので、実際のドキュメントでも確かめる。アプリのドキュメント表示の下に「Markdown 往復チェック」を置いてあり、取得した `plain` と TipTap の出力の行単位の差分が見られる。脚注、タスクリスト、画像などの結果は、ここで集めて追記する。
- 「属性を外して送った場合にサーバーがどう扱うか」は、更新 API が使えるようになってから確かめる（③）。

**調査3**：レート制限は、プラン（無料・有料）と種類（Read / Update / Search / Icon）ごとに異なり、公開ドキュメントには具体的な数値が書かれていない。

- 実際の値は `GET /api/v2/rateLimit` で取得できる（ドキュメントの例では Read 600 回/分、Update 150 回/分。ただしあくまで例）。
- 制限はユーザー単位（API キー単位ではない）。超えると 429（エラーコード 13）が返る。
- レスポンスヘッダ `X-RateLimit-Remaining` / `X-RateLimit-Reset` で残り回数がわかる。
- ポーリング間隔は、試作用スペースで `rateLimit` の値を確認してから決める。

**実ドキュメントでの確認（2026-11-07）**：実際のスペースで表示したところ、Backlog が `plain` に出力する独自の記法を TipTap が解釈できず、記法がそのまま文字として表示された。

| 記法 | 例 |
| --- | --- |
| 見出しの ID | `## 見出し {#abc}` |
| 日付メンション | `[dateMention label="2026/08/14" date="2026-08-14T00:00:00+09:00" mentionType="inline"]` |

## 12. テスト方針

- **`doc-sync-engine`**：`plan_push` と 3者マージを、表形式のテストケースで網羅する。対象は、リモート未変更、リモートのみ変更、両方変更（重ならない／重なる）、送信内容が現状と同じ場合。
- **`backlog-api`**：実際の API レスポンスを JSON のフィクスチャとして保存し、デシリアライズを確認する。HTTP のモックは、必要になるまで入れない。
- **結合テスト**：試作用スペースに対して手動で確認する。手順は、この文書に追記する。
